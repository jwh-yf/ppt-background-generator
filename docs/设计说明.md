# pptbg 设计说明：为什么这么做

这份文档记录**决策本身**，不重复代码里已有的注释。目的是让评审核查时能看懂每个决定背后的取舍，
而不是面对一堆「显然是这么写的」代码。

技术报告讲「是什么、结果如何」；这里讲「当时有哪些选项、为什么选了这个、代价是什么」。

---

## 1. 为什么不做「通用文生图套一层界面」

规则手册明确把「仅调用通用模型接口、简单部署现有项目、更换界面」排除在充分完成的作品之外。
更实际的问题是：那样做出来的东西**真的不好用**——通用模型追求细节丰富与高对比，与「底图上要压字」
这一使用场景的核心约束正好相反。提示词工程能缓解，但模型手里没有「哪里要放字」这条信息。

所以本项目的技术路线是从这个约束**反推**出来的：

1. 既然要控制留白，就得能**度量**它 → 定义安全区与 `safe_zone_std`；
2. 既然要模型学会它，就得有**带标注**的训练数据 → 程序化合成（标注是渲染时的构造参数，无标注噪声）；
3. 既然模型只是「倾向于」留白，就得有**硬约束** → 推理后按安全区做自适应柔化；
4. 既然要证明有用，就得有**可对比的评测** → 五个后端 × 六项指标。

四个环节互相咬合，缺任何一个都会退化成「生成一张图」而不是「生成一张能用的 PPT 背景」。

## 2. 为什么用合成数据（以及代价）

### 选项
| 方案 | 优点 | 致命问题 |
|---|---|---|
| 抓取 CC0 图库（Unsplash/Pexels 等） | 图好看、真实 | **没有安全区标注**；且「公开可访问不等同于当然具有复制、训练、改编或再分发授权」，需逐一核查每个来源的授权版本，存在否决级风险 |
| 人工标注真实图的安全区 | 图真实且有标注 | 600 张的标注成本对个人参赛者不现实，且标注主观性会引入噪声 |
| 程序化合成 | 零版权风险、标注免费且精确、可平衡、可复现 | 视觉复杂度低于真实照片 |

选第三条。代价诚实写进技术报告第 7 节：模型学到的是合成分布上的先验，对真实摄影素材的泛化未验证。

### 最强的理由不是版权，是「配对标注」

上面那张表里，抓取 CC0 图库的致命问题被写成了两个，但它们的份量并不相同，值得分开说清楚。

**版权是防守性的**：它说明「风险小」，不能说明「非这么做不可」。而且它不是零——本项目的 LoRA
挂在 SD 1.5 上训练，SD1.5 的权重本身带 CreativeML OpenRAIL-M 许可，其训练数据来源同样有争议。
我们的做法是「不重分发基座、只分发自己训出的 adapter」，把风险面收窄，而不是消除。
所以准确表述是**「把训练数据这一层的侵权风险消掉了」**，不是「保证没有版权纠纷」。说满了会被反问。

**真正非它不可的理由是标注**：

- 从图库抓一张背景图，能得到**一张图**。
- 但得不到：这块区域能压多亮的字、标题该放哪、面板边界在哪、局部对比度是多少。

没有任何公开数据集会附带「这张图的第 96~1248 列适合压白字」这种标注。而本项目的训练记录是这样：

```json
"safe_zones": [
  {"x": 96, "y": 120, "w": 1152, "h": 360, "region": "title", "contrast_std": 11.4},
  {"x": 96, "y": 520, "w": 1152, "h": 420, "region": "body",  "contrast_std": 14.8}
]
```

图像与标注是**同一次渲染的两个产物**——因为画面是我们自己画的，所以画的时候就知道面板落在哪、
留白留在哪、那块区域的局部对比度是多少。标注在这里不是事后人力补的，是构造参数本身，因此
**没有标注噪声，也没有标注成本**。

一句话版本：

> 我们不是找不到干净的图，是找不到带标注的图。安全区的位置必须和图像同时被生成出来，
> 所以训练数据只能自己造。

### 一个由此产生的连锁设计
母图也是程序化合成的（216 张，六类各 36 张），而不是下载来的。这让「素材来源」这一栏在合规
清单里可以干净地写成 `team-owned`，整条数据链路不存在第三方权利。

### 必须正面回答的质疑：数据自己造，模型学的是不是「自己的生成器」？

这是本方案唯一的真正软肋，不能回避。**回应是：目标分布本来就不是自然图像。**

我们要模型学的是**演示稿背景的设计语言**——六种场景色调、四种版式、安全区留白规则。
这套语言是人定的设计规则，不是自然照片的统计分布；用真实照片反而是在教它一件不相关的事。
合成数据在这里不是「退而求其次」，它就是正确的监督信号。

这个回应是可验证的，不是话术：评测里 `procedural` 后端就是「照规则画」的基线（同一套渲染代码，
不经过模型）。LoRA 要证明的不是「能画得像规则」，而是**在规则之上比规则画得更好、更多样**——
这正是 `lora` 与 `procedural` 两个后端并排比较的意义。若 LoRA 打不过 `procedural`，
就说明这层学习没有产生增量，这一点在技术报告的评测结果里是公开的。

## 3. 为什么是 LoRA，而不是全量微调或 DreamBooth

- **可复现性是评分维度**：全量微调 SD1.5 需要 A100 级硬件，评审无法复现；LoRA 在 8GB 显存的
  消费级卡上数小时可跑完。
- **权重可随作品开源**：LoRA 权重十几 MB，可以直接放进作品压缩包；全量权重几个 GB，只能给下载脚本。
- **任务性质匹配**：要注入的是「场景语义 → 影调 + 留白版式」的构图先验，属于风格/构图层面的调节，
  不是要模型学会一个新概念或新主体——这正是 LoRA 擅长的。
- **不选 DreamBooth**：它偏向「把某个具体主体注入模型」，与本任务要的「一类构图倾向」不符。

## 4. 为什么只训注意力投影层、不动 text encoder

`to_q / to_k / to_v / to_out.0` 是社区验证过的性价比最高的一组。理由：本任务要改变的是
「同样的提示词，画面结构不同」，这是**空间组织**层面的调整，发生在注意力对潜空间的调制上，
而不是词向量语义层面。不动 text encoder 还有一个工程好处：训练时不必回传文本侧梯度，
显存与时间都省一半，且不会有「把提示词理解能力训坏」的风险。

## 5. 为什么训练分辨率是 512

SD1.5 的原生训练分辨率。直接在 1024 上训 LoRA 会显著变慢，并且对 600 张的数据规模而言
更容易过拟合到具体样本。出图时再用高清放大流程到 1920×1080——分辨率需求由**推理侧**满足，
而不是靠训练侧硬扛。

## 6. 为什么自己写训练循环与 Web 后端

这条决定的出发点是**合规成本**，不只是技术偏好：

- 每引入一个框架，就要在《开源及第三方资源使用清单》里多一条「名称/版本/许可证/关键义务」，
  并多一份潜在的许可证冲突风险；
- 用 `diffusers` 自带的 `Trainer` 或 `accelerate` 的高级封装，会让「哪些是自研、哪些是调用」
  变得难以自证，而清单里恰恰要求写清**自研边界**；
- 训练循环只有百来行，Web 后端是标准库 `http.server`——评审可以逐行读完，这对「可核验」是加分项。

代价：自己维护的代码更多，需要自己处理 fp16 溢出、梯度累积、checkpoint 续训这些细节。
这些都在代码注释里写明了做法与原因。

## 7. 为什么把安全区做成「后处理约束」而不是生成时的强约束

生成时的强约束（例如在 UNet 里做区域引导）需要改模型结构与训练目标，会带来：
训练复杂度上升、与 LoRA 的兼容性风险、以及更难解释的实现。

后处理的代价是：模型只是「倾向于」留白，不保证，因此需要最后一道闸。
选择后处理的理由：

- **可解释**：安全区是一个矩形加一个统计量，网页上能画出框、能量出数，用户看得见；
- **可调**：`safe_zone_target_std` 是一个明确旋钮，不同汇报场景可以调松调紧；
- **不侵入模型**：LoRA 权重保持纯粹，换个模型或换个约束策略都不必重训。

体检里 `C3` 的计数就是这条路线代价的量化：600 张里有 21 个安全区（1800 个中的 1.2%）超标，
需要二次柔化才能达标。

## 8. 数据集体检为什么要写成脚本（而不是看几张图）

因为「看几张图觉得还行」在评测里拿不到分，也发现不了真问题。事实是：

- 第一版生成器在肉眼看来完全正常，**600 张里有 118 张被感知哈希判成近似重复**（19.7%），
  重复的训练样本等于变相放大权重，是典型的训练事故；
- 体检脚本还抓出了校验器自己的一个 bug（拿内部 key 去匹配人类可读的 caption，600/600 全误报）。

这两件事都只有把判据写死、批量跑，才会被发现。所以六类判据（完整性/分布/安全区/亮度/重复/溯源）
和它们的阈值都集中写在 `validate_dataset.py` 顶部，便于在报告里逐条引用、也便于评审改阈值重跑。

## 9. 评测里为什么必须有 `noise` 这个下界

因为「我们的指标很高」有两种可能：作品真的好，或者指标本身没有区分度、给什么都高分。
放一个随机低对比噪声后端进去，如果它的安全区指标也「合格」，那说明阈值定错了。

同理 `sd_base`（不加载 LoRA）回答「LoRA 到底带来了什么」，`procedural`（合成算法直接当生成器）
回答「训了模型比套模板强在哪」。**没有消融的评测不是评测，是宣传。**

## 10. 已知取舍一览

| 取舍 | 换来什么 | 放弃了什么 |
|---|---|---|
| 合成数据 | 零版权风险、精确标注、可平衡、可复现 | 真实照片的视觉复杂度与泛化能力 |
| 6 套预设 | 风格统一、可度量、可评测 | 覆盖不了所有汇报风格（扩展方式 = 加预设） |
| 只训 16:9 | 训练与评测聚焦，结论可靠 | 4:3 / 9:16 属域外，效果弱 |
| 后处理约束 | 可解释、可调、不侵入模型 | 需要最后一道闸，少数样本仍需二次柔化 |
| 自写循环与后端 | 依赖少、自研边界清晰、可逐行读完 | 自己维护更多代码与数值细节 |
| 标准库 Web | 无构建步骤、部署门槛低 | 没有现成的组件库与进度条，前端手写更多 |
